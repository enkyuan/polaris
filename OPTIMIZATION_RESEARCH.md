# Polaris runtime research memo

The latest reported practice result is **1.44 s**. The time to beat is **1.17 s**. Matching it requires removing 270 ms, or 18.75% of the current wall time. The working target is **1.10 s** to leave 70 ms for scorer variance and the earlier-submission tiebreaker. A 0.95–1.00 s stretch target depends on the native read floor and the cost of the two data redistributions.

## What the machine has to do

The scorer provides eight pinned logical vCPUs on Google Cloud N2 with Cascade Lake or newer Xeon and AVX-512, 24 GB RAM without swap, and a read-only input mount. The Linux/amd64 container runs as UID 1000 with no network and a read-only root. It can use a 64 MB memory-backed `/tmp` and 50 GB combined scratch and output. The image has an 8 GB limit and a 10-minute build limit. The run allows 4,096 processes and threads and 50 MB of stdout. Timing starts at container start and ends at process exit, including input and Parquet writes. Practice has about 20M generated events. The final uses a new dataset of about 60M events and caps each run at 3 minutes. [Google Cloud N2 machine series](https://docs.cloud.google.com/compute/docs/general-purpose-machines#n2-and-n2d_series)

The generated seed-17 practice proxy has these sizes. Output is from the current pipeline.

On this shape, 1.17 s needs at least **1.64 GB/s of input** and about **23.6M physical rows/s**. At 1.10 s the requirements rise to 1.75 GB/s and 25.1M rows/s. At a hypothetical 3.0 GHz, eight vCPU counters over 1.10 s would sum to 26.4 billion logical cycle slots, or about 955 per physical row. Clock rate, shared execution resources on SMT siblings, and time spent blocked determine how much work fits in those slots.

The wall-time floor is at least the largest of the sustained input-read time, output-write time, total compute and memory demand divided by effective throughput, and the serial dependencies left after overlap. Measure the read and structural-scan floors separately. The M1 read-only probe on this sample took 0.08–0.09 s warmed and 2.12 s on its first read. The lexical scan took about 0.25–0.27 s warmed. Native N2 input and output placement, page-cache state, physical-core topology, and phase timings are unmeasured. STREAM bandwidth is a ceiling reference for sequential memory traffic. The pipeline also has random probes and page faults. [McCalpin, STREAM](https://www.cs.virginia.edu/stream/ref.html) · [Crotty et al., Are You Sure You Want to Use MMAP in Your Database Management System?](https://cs.brown.edu/people/acrotty/pubs/p13-crotty.pdf)

| --- | ---: |
| CSV projection, validation, and overlapped linked IDs | 0.49 s |
| Earliest-version reduction and person partitioning | 0.21 s |

## Derived reductions

**Dense sessions reduce to time-cell endpoints.** Anchor half-open cells of width `G = 1,800,000` milliseconds at the manifest start. The largest possible gap between any two integer timestamps within one cell is `G − 1`. All events in a cell therefore belong to the same session. Process nonempty cells in order. The only possible break is `next.first − previous.last > G`. Counts and integer sums compose within each cell, including cents by category. The first endpoint of each connected chain is the unchanged session start. A cell can cross midnight because day attribution happens after the chain is built. The prototype used at most 2,048 cells and 64 categories, only for at least 16,384 events per person. On the 14-day proxy, a person uses at most 672 cells. The work is one event pass plus a bounded cell scan for a qualifying timeline.

**Whole-second ingest order leaves room for a fingerprint.** The four-digit Gregorian F1 range is roughly −62.2B to +253.4B seconds from the Unix epoch. Adding `2^37` makes every valid value nonnegative and smaller than `2^39`. The low 39 bits therefore preserve exact ingest order. The high 25 can retain hash bits that would otherwise be recomputed on both deduplication passes. Identical IDs have identical stored bits, including IDs represented by an external string reference. A collision only sends extra candidates through the exact table. Timestamp arithmetic for lateness still uses milliseconds.

**Date prefixes can classify some late rows.** The latest acceptable UTC ingest second for a valid event is `floor((event_ms + 86,400,000) / 1000)`. For a validated fixed-width F1 value, chronological order agrees with byte order. The ingest date alone decides the comparison unless it equals the cutoff date. A block decoder can use exact date-prefix matches, perform the within-day comparison on the remaining rows, and retain full validation and fallback. This removes part of the arithmetic for common cases and still needs to win against the current word-at-a-time F1 decoder.

**A proof of uniqueness can separate keys from payload routing.** A larger architecture trial would let producers write compact person-oriented payload batches and build private seen/repeated bitmaps keyed by event ID. Merge each worker with `repeat |= worker_repeat | (seen & worker_seen)` followed by `seen |= worker_seen`. A bit unset in the resulting repeat map proves that matching record is unique, provided every eligible candidate was observed. Reconcile set bits through exact ID argmin and suppress losers by stable row reference. Invalid winners must participate in this reduction. This avoids sending the full payload through both an ID partition and a person partition. It adds a candidate-resolution barrier and bitmap traffic. At `2^27` bits per map, eight workers with two maps each use 256 MiB before reduction. Prototype the private-bitmap merge and the payload savings against the existing, more cache-local ID buckets before replacing the pipeline.

**A guarded alphabet can shrink the keys without a dictionary lookup.** Two IDs of up to nine lowercase ASCII letters or digits each fit in 108 bits with a reversible six-bit alphabet. The remaining 84 bits of a 24-byte record can hold a 32-bit timestamp token, a 32-bit purchase payload, and a 20-bit signed ingest delta in whole seconds relative to that event's timestamp. A reserved delta can reference a wide record for invalid payloads, arbitrary bytes, and time deltas outside the small representation. This is a second packing option after the side-cursor experiment. The guards and repacking instructions have to cost less than the traffic they save. Test the six-bit operation as a microkernel first, including a BMI2 implementation where the CPU supports it. [Intel Intrinsics Guide](https://www.intel.com/content/www/us/en/docs/intrinsics-guide/index.html)

**Assists reduce to interval union.** For sorted session starts, each click covers an index interval `[lo, hi)` bounded by its timestamp and its timestamp plus seven days. Both endpoints advance monotonically as clicks advance. Per campaign, increment from `max(lo, covered_end)` to `hi`, splitting only at changes in the session start day. Touching and overlapping intervals are counted once. This is already in the current code. The remaining costs are click parsing, ordering, and the intervals actually contributing to output.

## Bottlenecks supported by traces

The latest M1 Time Profiler trace on seed 17 put 2,232 of 6,409 running-thread samples in event ingestion, or **34.8%**. The preceding trace had 40.1% event parsing, 12.7% click parsing, 5.3% linked IDs, 24.1% deduplication and person routing, and 16.2% grouping through user output. The ingestion change removed sampled candidate growth copies. Its warm five-run baseline median was 0.97 s. CPU sample shares exclude waiting and cannot be used as N2 wall-stage shares. See [the trace notes](PERFORMANCE.md#trace-guided-ingestion-changes).

At 32 bytes per event candidate, the proxy's physical rows put an upper bound of roughly 691 MB on the candidate stream before accounting for malformed rows. The pipeline writes that stream, reads it twice, and writes a new person stream. The parser has already removed some allocation copies. Eliminating one full payload pass or carrying previously computed metadata is a larger opportunity than making an already-linear assist sweep slightly faster.

For scale, if the M1 event-ingest sample share of 34.8% were an N2 wall share, then cutting only that stage would require eliminating about 54% of its time to reach 1.17 s. The measured share is from a different CPU, but the calculation explains why the experiment plan covers both parsing and data motion.

## Prototype results

I built independent C++ variants and ran them with eight workers on the Apple M1. All timing batches used the seed-17 20M input, a warmup, interleaved runs, and full output to Parquet. Each control belongs to its own batch.

| Trial | Runs per build | Control → variant median wall | Control → variant median user CPU | Decision |
| --- | ---: | ---: | ---: | --- |
| 24-byte event candidate with sparse purchase and overflow side arrays | 4 | 1.46 → 1.25 s | 5.50 → 5.85 s | Passed row comparison. Wall times ranged from 1.08 to 2.30 s across both builds. The CPU regression and variable wall time leave the result unresolved. |
| Cached 25-bit fingerprint in the ingest-order word | 6 | 0.99 → 1.02 s | 5.46 → 5.48 s | Removed repeated hashing for the fingerprint and showed no repeatable gain on this CPU. |
| Dense time-cell summaries | 6 | 0.99 → 1.05 s | 5.46 → 5.39 s | Demonstrated an exact sort-free path. Its local grouping-through-write median rose from 0.20 to 0.24 s. Keep the faster overall control. |
| Single candidate allocation per worker with per-bucket overflow | 6 | 1.09 → 1.26 s | 5.39 → 5.86 s | The simpler allocation schedule retained the slab through deduplication, and the local phase median rose from 0.25 to 0.39 s. |
| 128, 512, and 1,024 partitions versus 256 | 5 | 1.13 → 1.02, 1.09, 1.27 s | 5.48 → 5.47, 5.55, 5.79 s | The 128-partition version led this batch. The next seed-17 batch narrowed its lead to 1.09 → 1.06 s and increased its user CPU median from 5.39 to 5.55 s. |

The dense prototype matched an independent reference on 18,000 linked-person events spread across files with a non-midnight manifest start. The case includes an exact 30-minute merge across midnight, a 30-minute-plus-1-ms split, a purchase category tie, simultaneous ad clicks with different IDs, and the inclusive seven-day boundary. The upstream winner reduction also suppressed a later valid duplicate.

The 24-byte variant was also in the allocator batch. The control and packed medians were 1.09 and 1.14 s, with user CPU medians of 5.39 and 5.91 s. This repeated the extra CPU cost and reversed the first wall-time result. The selected implementation keeps the existing 32-byte candidate representation.

On an independent 20M-event seed 41, 128 partitions moved the median from 0.985 to 0.965 s over six runs per build. User CPU moved from 5.25 to 5.34 s and system CPU moved from 0.545 to 0.515 s. Both Parquet tables matched, with 2,226,017 user rows and 28,014 campaign rows. This supports a native A/B test for 128 partitions. The measured advantage on M1 is much smaller than the 270 ms target gap.

All five main prototypes passed the 36 official fixtures and four record-layout checks. Both tables matched the public dev answers and the current pipeline on seed 17. The scored source and Dockerfile stay at the control while the prototypes await a native comparison.

The local archive under `scratch/optimization-research-2026-11-20/` contains failure and success timings, prototype source patches against `58ee89a`, and the dense session case.

## Native experiment order

1. Run the current scorer image against a fresh output mount and record a cold read pass, a warmed read pass, a warmed structural scan, and interleaved full AVX2 and AVX-512BW runs. Capture container start-to-exit and binary phase times. Record affinity and the physical cores behind the pinned vCPUs. Where available, sample `task-clock`, cycles, instructions, faults, branch misses, and cache misses in separate profiling runs.
2. Compare 128 and 256 partitions under that same setup. Simultaneous bucket counts affect allocation, scatter locality, cache working sets, and the number of available jobs. The M1 results give a concrete candidate for the first native A/B. Use multiple seeds at practice size, then the 60M proxy. Verify both tables on every candidate, including the 36 fixtures, the public dev answer, and targeted boundary cases. Archive the exact commit, toolchain, selected ISA, row counts, and raw timing logs.
3. Spend the next rewrite on the dominant measured path. If structural input dominates, compare block-wide field extraction with the current scanner. If the two redistributions dominate, write person-oriented batches from each worker once aliases are ready, retain lightweight ID and order metadata, reconcile repeated IDs into a loser mask, and compact each person span once while merging workers. Track bytes written per physical event, the replica bitmap working set, and the critical-path cost of waiting for the alias map and the global repeat map. A useful first milestone is removal of one full payload pass and at least 100 ms of native end-to-end wall time.

The immediate decision is empirical. A 1.10 s target is credible enough to test, and the actual lower bound requires native measurements. One competition score cannot establish which part of the budget is currently being exceeded.
